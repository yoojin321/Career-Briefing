# Requirements — Career Briefing

AI 기반 취업 준비용 데일리 뉴스 브리핑 웹서비스. 뉴스 수집 → 중요도 평가 → AI 요약/분석 → 취업 활용 → 학습 기록으로 이어지는 개인용 뉴스 학습 플랫폼.

## 용어 (Glossary)
- **원본 기사 (Article)**: 외부 소스에서 수집한 뉴스 메타데이터 (제목, URL, 언론사, 발행일 등).
- **브리핑 (Briefing)**: 특정 날짜에 선정된 추천 뉴스 묶음 (날짜별 1개, 결과 고정 저장).
- **분석 (Analysis)**: 특정 기사에 대한 AI 생성 결과물 (요약, 배경, 취업 활용 등). 기사와 분리 저장.
- **수집 작업 (Ingestion Job)**: 외부 소스에서 기사를 가져오는 작업.
- **발행일 (publishedAt)**: 언론사가 기사를 발행한 시각.
- **수집일 (collectedAt)**: 본 서비스가 기사를 가져온 시각.

## Requirement 1 — 뉴스 자동 수집 (Phase 1)
**User Story:** 사용자로서, 실제 최신 한국어 뉴스가 합법적인 경로로 자동 수집되기를 원한다. 그래야 신뢰할 수 있는 최신 이슈를 학습할 수 있다.

### Acceptance Criteria
1. WHEN 수집이 실행되면 THEN 시스템은 외부 뉴스 소스(네이버 뉴스 검색 API 및/또는 공식 RSS)에서 실제 기사를 가져온다.
2. 시스템은 기본적으로 최근 24~48시간 발행 기사를 수집하며, 유효 기사가 부족하면 최대 7일까지 범위를 확장한다.
3. 시스템은 각 기사에 대해 제목, 원문 URL, 언론사, 발행일, 수집일, 카테고리를 저장한다.
4. 시스템은 발행일과 수집일을 항상 구분하여 저장한다.
5. 시스템은 동일 URL 및 동일 사건(제목 유사도 기준) 기사를 중복 제거한다.
6. 시스템은 소스별 수집 어댑터(adapter)를 분리하여 향후 소스 추가가 가능하도록 설계한다.
7. WHEN 기사 본문을 합법적으로 확보할 수 없으면 THEN 제목과 공식 제공 메타데이터만 저장하고, 본문 없음 플래그를 기록한다.
8. 시스템은 원문 전체를 복제·재배포하지 않는다.
9. WHEN 수집이 실패하면 THEN 시스템은 오류를 작업 로그에 기록하고 재시도 로직을 수행한다.
10. WHEN 외부 API 키가 설정되지 않았으면 THEN 시스템은 명시적 오류/안내를 반환하고, 임의 뉴스를 실제 기사처럼 표시하지 않는다.

## Requirement 2 — 뉴스 카테고리 분류 (Phase 1)
**User Story:** 사용자로서, 뉴스가 5개 카테고리로 분류되기를 원한다. 그래야 분야별로 균형 있게 학습할 수 있다.

### Acceptance Criteria
1. 시스템은 다음 5개 카테고리를 지원한다: IT/AI, 경제/금융, 시사/사회, 산업/기업, 정책/공공기관.
2. 시스템은 각 수집 기사를 하나의 주 카테고리로 분류한다.
3. 분류는 소스 질의 키워드 및 규칙 기반으로 수행하며, 근거를 저장한다.

## Requirement 3 — 뉴스 선정 알고리즘 (Phase 1)
**User Story:** 사용자로서, 하루 뉴스가 단순 무작위가 아닌 가중치 기반으로 선정되기를 원한다. 그래야 학습 가치가 높은 뉴스를 받는다.

### Acceptance Criteria
1. 시스템은 최신성(25%), 사회·산업적 중요도(30%), 취업 준비 활용도(30%), 카테고리 다양성(15%) 가중치로 기사별 점수를 계산한다.
2. 가중치는 설정 가능한 상수로 구현한다.
3. 선정 파이프라인은 다음 순서를 따른다: 후보 수집 → 유효성/출처 검증 → 중복 제거 → 중요도/취업연관성 평가 → 카테고리 다양성 고려 최종 선정 → 날짜별 저장.
4. WHEN 특정 날짜의 브리핑이 이미 저장되어 있으면 THEN 재실행해도 동일한 결과를 반환한다 (결과 고정).
5. 하루 추천 기사 수 기본값은 3이며, 1~10 범위에서 설정 가능하다.
6. 시스템은 각 선정 기사에 대해 점수 및 선정 근거(사유)를 구조화 데이터로 저장한다.

## Requirement 4 — AI 뉴스 분석 (Phase 1)
**User Story:** 사용자로서, 선정 뉴스에 대해 요약·배경·취업 활용·면접 질문까지 AI 분석을 받고 싶다. 그래야 취업 준비에 바로 활용할 수 있다.

### Acceptance Criteria
1. 각 선정 기사에 대해 다음 항목을 생성한다: 핵심 요약(3줄 이내), 배경/원인, 핵심 개념(2~3개), 산업/기업 영향, 취업 활용 포인트, 예상 면접 질문(기본1+심화1, 각 답변 포인트3+예시답변), 출처.
2. AI는 확보한 출처 정보만을 기반으로 작성하며, 근거 없는 수치·인용·기관 입장을 생성하지 않는다.
3. 기사에 없는 전망은 "분석/예상"으로 명확히 구분 표기한다.
4. 근거가 부족하면 "확인 필요"로 표기한다.
5. WHEN 기사 제목만 확보된 경우 THEN 상세 배경을 사실처럼 생성하지 않고 제한적 분석 + 확인 필요 표기를 한다.
6. 시스템은 AI 생성 결과를 Zod 스키마로 검증한다.
7. WHEN 검증이 실패하면 THEN 최대 N회 재시도하고, 그래도 실패하면 분석을 "실패" 상태로 저장한다.
8. 시스템은 각 기사의 AI 분석 완료/실패/진행중 상태를 사용자에게 표시한다.
9. WHEN LLM API 키가 없으면 THEN 분석은 "미설정" 상태로 표시되고 설정 안내를 제공한다 (가짜 분석 생성 금지).

## Requirement 5 — 메인 대시보드 (Phase 1)
**User Story:** 사용자로서, 오늘의 주요 이슈를 카드로 한눈에 보고 싶다.

### Acceptance Criteria
1. 상단에 로고/이름, 오늘 날짜, 설정 버튼, 저장한 뉴스 바로가기를 표시한다.
2. "오늘의 주요 이슈" 아래 선정 뉴스 카드를 표시한다.
3. 각 카드는 카테고리, 제목, 2~3줄 요약, 발행일, 출처, 선정 순위/사유를 표시한다.
4. 카드 클릭 시 상세 분석 페이지로 이동한다.
5. 하단에 "다른 뉴스 보기", "과거 브리핑 보기", "저장한 뉴스" 링크를 제공한다.
6. 로딩/빈 데이터/수집 실패/분석 실패 상태 화면을 각각 제공한다.

## Requirement 6 — 뉴스 상세 페이지 (Phase 1)
**User Story:** 사용자로서, 선정 뉴스의 전체 AI 분석을 섹션별로 읽고 싶다.

### Acceptance Criteria
1. 상세 페이지는 제목/원문정보, 3줄 요약, 배경/원인, 핵심 개념, 산업·기업 파급효과, 취업 활용 포인트, 예상 면접 질문/답변, 원문 바로가기, 북마크/학습완료 버튼을 포함한다.
2. 사실과 AI 해석("분석/예상")을 시각적으로 구분한다.
3. 원문 링크는 새 탭으로 열린다.

## Requirement 7 — 날짜별 저장 및 조회 (Phase 1)
**User Story:** 사용자로서, 과거 브리핑을 날짜별로 다시 볼 수 있기를 원한다.

### Acceptance Criteria
1. 브리핑은 날짜 키로 저장되어 재조회 시 동일 결과를 반환한다.
2. 기사와 AI 분석은 분리 저장되어 분석만 재생성할 수 있다.

## Requirement 8 — 사용자 설정 (Phase 2)
**User Story:** 사용자로서, 관심 분야/뉴스 개수/선정 방식/분석 깊이/다크모드를 조절하고 싶다.

### Acceptance Criteria
1. 관심 카테고리 on/off, 하루 뉴스 개수(1~10), 선정 방식(균형/관심우선/랜덤), 분석 깊이(간단/상세), 다크모드를 설정할 수 있다.
2. MVP에서는 로그인 없이 브라우저(localStorage)에 설정을 저장하며, 향후 계정/클라우드 동기화를 확장 가능하도록 설계한다.

## Requirement 9 — 아카이브/북마크/검색 (Phase 2)
### Acceptance Criteria
1. 날짜별 이전 브리핑 조회, 카테고리 필터, 키워드 검색, 최신순 정렬, 북마크만 보기를 지원한다.
2. 북마크 및 학습 완료 상태를 저장한다.

## Requirement 10 — 보안/운영 (Phase 1)
**User Story:** 운영자로서, API 키가 노출되지 않고 관리자만 수집을 실행할 수 있기를 원한다.

### Acceptance Criteria
1. 외부 뉴스 API 및 LLM 호출은 서버에서만 수행하고 API 키를 클라이언트에 노출하지 않는다.
2. 수동 수집/분석 트리거 엔드포인트는 관리자 시크릿(헤더/토큰)으로 보호한다.
3. 환경변수는 `.env.example`에 문서화한다.
4. 스케줄러가 없거나 실패해도 관리자가 수동으로 수집을 실행할 수 있다.

## Requirement 11 — 품질/검증 (Phase 1)
### Acceptance Criteria
1. TypeScript 타입 체크 및 빌드가 성공한다.
2. 핵심 로직(선정 알고리즘, 중복 제거, 스키마 검증, 수집 어댑터 파싱)에 대한 단위 테스트가 존재하고 통과한다.
3. README에 로컬 실행, 환경변수, 뉴스 API 설정, 스케줄러, 배포 방법을 문서화한다.
